# Tooltip

A tooltip describes the control it is attached to, on a temporary surface anchored to it.
It follows the [Material Design 3 Tooltip](https://m3.material.io/components/tooltips/overview) specification.

Tooltip renders through [Portal](./portal.mdx), so your app must be wrapped in a `PortalHost` once
at the root. It claims the `PORTAL_LAYERS.tooltip` layer, the topmost one, because a tooltip can
describe a control in any layer below it.

There are two variants. **Plain** is a line of text that appears on a hover or a long press of
the control, and takes itself down after 1.5s. **Rich** adds a subhead and actions, and stays up
until you dismiss it.

## Usage

Pass the control as `anchor` and the text as children.

<SnackExample
  name="RootNative Tooltip — Usage"
  code={`
  import { IconButton, PortalHost, Tooltip } from '@rootnative/components'
  import { mdiResolver } from '@rootnative/components/mdi'
  import { ThemeProvider } from '@rootnative/core'
  import { SafeAreaProvider } from 'react-native-safe-area-context'
  import { View } from 'react-native'

  function Screen() {
    return (
      <View style={{ flex: 1, flexDirection: 'row', alignItems: 'center', justifyContent: 'center', gap: 8 }}>
        <Tooltip anchor={<IconButton icon="heart-outline" accessibilityLabel="Favourite" />}>
          Add to favourites
        </Tooltip>
        <Tooltip anchor={<IconButton icon="share-variant" accessibilityLabel="Share" />}>
          Share
        </Tooltip>
        <Tooltip
          side="bottom"
          anchor={<IconButton icon="archive-outline" accessibilityLabel="Archive" />}
        >
          Move to archive
        </Tooltip>
      </View>
    )
  }

  export default function App() {
    return (
      <SafeAreaProvider>
        <ThemeProvider iconResolver={mdiResolver}>
          <PortalHost>
            <Screen />
          </PortalHost>
        </ThemeProvider>
      </SafeAreaProvider>
    )
  }
`}
/>

The anchor renders where the `<Tooltip>` sits in your tree, inside a measuring view that watches
for hover. A string or a number passed as children, also text with `{expressions}`, gets the
supporting-text style of the variant. Anything else renders as given, so text beside an element
needs its own `Text`.

## Triggers

| Input | Behaviour |
|-------|-----------|
| Hover in | Shows the tooltip. Hover out hides a plain tooltip. A rich tooltip stays up, so the pointer can reach its actions |
| Focus | Shows the tooltip on web, so a Tab stop reads the same as a hover. Blur hides a plain tooltip. A rich tooltip stays up, so Tab can reach its actions |
| Escape | Hides the tooltip while the anchor has focus. The key stops there, so an enclosing dialog does not close on the same press |
| Long press | Shows the tooltip. This is how touch devices reach it. On web, only on a device with no hover, or on an anchor with its own `onLongPress` |
| Press | Hides the tooltip. A tap is the control at work, not a request for help text |
| Timeout | Hides a plain tooltip after `duration` (1500ms). Rich tooltips never time out |
| Outside press / Android back | Hides a rich tooltip. A plain one has no dismiss region to press |

The tooltip injects the long press and the focus pair into the anchor itself, so the anchor must
accept `onLongPress`, `onFocus` and `onBlur`. Every Root Native pressable does, and its own
handlers still fire. The wrapper catches hover instead, because every Root Native pressable drives
its state layer from `onHoverIn`/`onHoverOut` and would overwrite an injected pair.

On web, react-native-web cancels the click of a mouse press that is held for the long-press delay.
So on web the tooltip adds the long press only when no input can hover, or when the anchor has an
`onLongPress` of its own. A slow mouse click on the anchor still presses it.

MD3 takes a plain tooltip down 1.5s after it appears, whether or not the pointer is still on the
anchor. Pass `duration={0}` to keep it up until a hover out or a press instead.

## Rich

`variant="rich"` adds a `subhead` above the text and an `actions` row below it, and makes the
tooltip persistent. It waits for an outside press, an action, or the Android back button. Its
surface takes touches, unlike a plain tooltip.

<SnackExample
  name="RootNative Tooltip — Rich"
  code={`
  import { Button, IconButton, PortalHost, Tooltip } from '@rootnative/components'
  import { mdiResolver } from '@rootnative/components/mdi'
  import { ThemeProvider } from '@rootnative/core'
  import { SafeAreaProvider } from 'react-native-safe-area-context'
  import { useState } from 'react'
  import { Text, View } from 'react-native'

  function Screen() {
    const [open, setOpen] = useState(false)
    return (
      <View style={{ flex: 1, alignItems: 'center', justifyContent: 'center', gap: 16 }}>
        <Tooltip
          variant="rich"
          subhead="Rich tooltip"
          actions={<Button variant="text">Learn more</Button>}
          anchor={<IconButton icon="information-outline" accessibilityLabel="About sync" />}
        >
          Rich tooltips bring attention to a feature that warrants a sentence of explanation.
        </Tooltip>

        <Tooltip
          visible={open}
          onDismiss={() => setOpen(false)}
          variant="rich"
          subhead="Controlled"
          actions={<Button variant="text" onPress={() => setOpen(false)}>Got it</Button>}
          anchor={<Button variant="tonal" onPress={() => setOpen(true)}>Show help</Button>}
        >
          visible + onDismiss put you in charge — the anchor stops opening it by itself.
        </Tooltip>
      </View>
    )
  }

  export default function App() {
    return (
      <SafeAreaProvider>
        <ThemeProvider iconResolver={mdiResolver}>
          <PortalHost>
            <Screen />
          </PortalHost>
        </ThemeProvider>
      </SafeAreaProvider>
    )
  }
`}
/>

`subhead` and `actions` are rich-only. On a plain tooltip they log a development error and render
nothing. A plain tooltip is one line of text.

## Controlled

Pass `visible` and `onDismiss` to drive the visibility yourself. The anchor then stops opening
the tooltip. You wire hover and long press yourself. That is how you attach a tooltip to
something that isn't a press at all: a form error, or a first-run hint.

A dismissal that doesn't come from the anchor still reports itself, so a controlled tooltip
behaves like every other overlay in the library:

- The outside press and the Android back button of a rich tooltip call `onDismiss`.
- The timeout of a plain tooltip calls `onDismiss` after `duration`. Pass `duration={0}` if you
  want the tooltip to stay up until you take it down.

## Placement

`side` and `align` are preferences, not commands.

| Prop | Values | Default | Meaning |
|------|--------|---------|---------|
| `side` | `'top' \| 'bottom'` | `'top'` | The side of the anchor that the tooltip prefers |
| `align` | `'start' \| 'center' \| 'end'` | `'center'` | The cross-axis alignment against the anchor |
| `offset` | `number` | `4` | The gap between the anchor edge and the tooltip, in dp |
| `screenMargin` | `number` | `8` | The minimum distance the tooltip keeps from every screen edge |

`align` is **logical**: `'start'` is the left edge of the anchor in LTR, and its right edge in RTL.

A tooltip that doesn't fit on its preferred side flips to the other side, but only when that side
has more room. Horizontally it shifts back inside the margin, and doesn't flip. The tooltip
measures the window coordinates of the anchor when it opens. It doesn't follow the anchor while a
scroll view moves underneath it.

Like a menu, a tooltip is confined to the overlay layer it renders into. That is why the root of
your app is the right place for `PortalHost`; see
[the note on menu placement](./menu.mdx#the-menu-is-confined-to-its-portalhost). Keep a tooltip
short. A plain one caps at 200dp wide, a rich one at 320dp, and neither exceeds the space available
on the side it resolved to.

## Overrides

| Prop | Target |
|------|--------|
| `containerColor` | The tooltip surface background |
| `contentColor` | The supporting text, plus the subhead on a rich tooltip |
| `style` | The tooltip surface |
| `textStyle` | The supporting-text `Text` only |
| `anchorStyle` | The view wrapping the anchor |

The tooltip surface draws no state layer of its own, so there is nothing to derive from
`containerColor`. It only recolors the surface. You color the nodes you pass as `children` or
`actions` yourself.

## Tokens

| Token | Plain | Rich |
|-------|-------|------|
| Container | `inverseSurface`, corner 4dp (`cornerExtraSmall`) | `surfaceContainer`, corner 12dp (`cornerMedium`), elevation level 2 |
| Subhead | — | `titleSmall` / `onSurfaceVariant` |
| Supporting text | `bodySmall` / `inverseOnSurface` | `bodyMedium` / `onSurfaceVariant` |
| Padding | 8dp horizontal, 4dp vertical | 16dp horizontal, 12dp vertical |
| Size | min 40×24dp, max 200dp wide | min 40×24dp, max 320dp wide |
| Gap to anchor | 4dp | 4dp |
| Duration | 1500ms | Persistent |

A plain tooltip carries no elevation in MD3. The inverse surface is what separates it from the
content behind. The actions are start-aligned, the opposite of the actions of a [dialog](./dialog.mdx).

## Motion

The tooltip fades in and out on `springFastEffects`, with no scale, unlike a menu. It collapses to
a hard cut under reduced motion; see [Motion](../motion.md).

The surface stays invisible for the frame between the mount and the measurement. Its own size
decides which side it lands on, so it must be laid out before the component can place it.

## Accessibility

- The surface reports `role="tooltip"` and announces itself as a polite live region when it appears.
- The surface of a plain tooltip never takes touches, so it can't stand between the user and the
  control it describes. The surface of a rich tooltip does, and the region that catches outside
  presses is announced as a button labelled "Close tooltip". Override it with `dismissAccessibilityLabel`.
- **On web**, the anchor carries an `aria-describedby` that points at the tooltip while it is
  shown. That is the only thing that connects the two: the surface renders in a portal, far from
  the anchor in the DOM. React Native has no equivalent, so this is web-only. A plain tooltip
  whose text is the `accessibilityLabel` or the `aria-label` of the anchor adds no description,
  so a screen reader says the name one time.
- The wrapper around the anchor stays out of the accessibility tree, so the role and the label of
  the anchor are the only things a screen reader sees. A tooltip is supplementary: an icon-only
  button still needs its `accessibilityLabel`. The tooltip text can be that label, as on an MD3
  icon button, or it can add to it.
- **On web**, keyboard focus on the anchor shows the tooltip, and Escape hides it, so a keyboard
  user reaches the same text as a pointer. Focus inside the actions of a rich tooltip doesn't
  close it.
- Hover, focus and long press are supplementary. Anything a user must read to operate the control
  belongs in the UI or in the label of the anchor, not only in a tooltip.
